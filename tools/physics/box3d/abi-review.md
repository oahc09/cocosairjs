binding is reference-only and has not been claimed as compiled or migrated.

## Function, callback, layout and semantic disposition

`abi-diff.json`, regenerated by `review-abi.mjs`, identifies 18 removed and 36
added public `B3_API` declarations. Two declarations change spelling/signature:
`b3GetByteCount` returns int64 instead of int32; the other changes only a parameter
name. This parser does not claim to audit callback typedefs or struct layouts.

1. COM getters become `b3Body_GetLocalCenter` and `b3Body_GetWorldCenter`. The new
   foundation calls the target names directly; its body origin and COM are distinct.
2. `b3CreateCompoundShape` becomes `b3CreateBakedCompoundShape`; player construction
   and destruction become `b3CreatePlayer` / `b3DestroyPlayer`. Importantly, despite
   an intermediate commit message, the final target still names the _data_ creator
   `b3CreateCompound`. Do not blindly replace that name from commit descriptions.
3. Triangle narrow-phase entry points change from capsule/hull/sphere-and-triangle
   to triangle-and-capsule/hull/sphere. Argument order and normal orientation require
   explicit adaptation, not symbol-only replacements. The old binding also refers
   to removed `b3World_RebuildStaticTree`. All nine stale binding references are
   enumerated in the generated report. These capabilities are not exposed by the
   narrow foundation, and full T04 remains outstanding.
4. Allocator callback size changes int32 to size_t; free callback gains size_t.
   Global byte count and `b3Counters.byteCount` become int64, with the latter moving
   to the first field. The foundation writes low/high uint32 words and JS returns
   bigint, never truncating to signed int32 or packing a 64-bit ID in Number.
5. Hull, mesh and height-field content hashes change 32 to 64 bits. Hull adds SOA
   arrays and edge cosine offsets, moves byteCount, and changes its version.
   Mesh version and tree representation also change. Baked compound serialization
   replaces old pointer-fixup conventions; compound material indices become
   pointer-plus-count uint16 arrays rather than a fixed-size int array. Old cooked
   bytes and caches are incompatible and are not reused.
6. `b3ManifoldPoint.baseSeparation` moves behind normalVelocity. The semantic order
   in an explicitly copied buffer may differ from native layout, but direct native
   offsets from the old build are invalid. Normal velocity is only computed when
   needed for hit events; totalNormalImpulse includes warm starting, substep delta,
   and restitution. No event/contact reader is exported until snapshot epoch tests
   cover nonzero rotation, offset COM, recycling and CCD. The foundation body
   snapshot is copied synchronously; it is not a contact snapshot contract.
7. New definitions include world restitution iterations/propagation and isotropic
   inertia tolerance, body safetyFactor, shape name/speculative-contact setting,
   extra plane-result indices, mesh input options and explicit padding. Definitions
   are always initialized with the target `b3Default*Def`, then reviewed fields are
   assigned; zero-filled old definition layouts are not copied across builds.
8. Debug draw `DrawShapeFcn` now returns void; drawAnchorA becomes bool and removed
   drawFrictionForces cannot be retained as if it still exists. Runtime names now
   use a name cache, affecting recording versions and lifetime. Debug draw,
   recording, cooked geometry and callback migration remain outside this slice.
9. Body/shape IDs use the public store/load helpers, with generation and world bits
   preserved. Native validation only promises a bounded generation range. JS
   ownership tokens additionally reject other module instances and destroyed worlds;
   IDs are not perpetual application collider identity. Contact IDs remain 12 bytes
   with a uint32 generation and must not be collapsed into a body-ID representation.
10. Box hull creation copies/deduplicates into the world's hull database:
    `shape.c` calls `b3AddHullToDatabase`, whose implementation in
    `physics_world.c:41` calls `b3CloneHull` on a new entry and reference-counts it.
    Therefore a stack `b3BoxHull` is safe for the narrow box constructor. This proof
    does not grant the same ownership semantics to every mesh/compound API.

`native/layout_probe.c` produces sizes, offsets, hash widths and selected enum
values for both header sets. Host 64-bit records are retained independently.
`layout-wasm.mjs` now compiles and executes this header-only probe on actual Node
WASM for both pinned header sets, each reporting pointerBytes=4. No old-core
physics implementation is linked. In `wasm32-layout-20261022-c`, old to target:

- WorldDef: 104 to 116 bytes; BodyDef: 96 to 100 bytes.
- ShapeDef remains 104 bytes, but internalValue moves from offset 96 to 100.
  Equal total size is not evidence of layout compatibility.
- Counters: 200 to 208 bytes; byteCount offset 44 to 0.
- HullData: 136 to 152; BoxHull: 440 to 696; MeshData: 88 to 96.
- MeshDef: 28 to 32; CompoundData: 120 to 96; ChildShape: 76 to 68.
- PlaneResult: 28 to 40. ManifoldPoint stays 56 bytes, with baseSeparation offset
  28 to 40, normalImpulse 32 to 28 and normalVelocity 40 to 36.
- Hull/mesh/height-field hash widths: 4 to 8 bytes. World/body/shape/contact IDs
  remain 4/8/8/12 bytes. These measurements do not authorize cooked-cache reuse.

The real ownership fixture also measures a critical ID boundary. Public body and
shape packing contains object index, world slot and object generation, but not the
world generation (`include/box3d/id.h`). In both fresh Debug and Release runs,
127 out of 127 subsequent world lifetimes revalidate the previous numeric body ID.
The facade's object-token/world ownership still rejects that old handle, preserving
the new body's snapshot and counts. Same-live-world 128-cycle reuse separately
increments object generation and rejects old IDs. Do not treat raw IDs as durable
collider identities, or interpret these finite samples as proof against all ABA.

## Build architecture

The host CMake `project` adds the fixed upstream core as a subdirectory. This avoids
its `PROJECT_IS_TOP_LEVEL` Emscripten pthread injection without changing core bytes.
The foundation uses C17, float32, SSE2/WASM SIMD, AVX2 off, `-fno-fast-math` and
`-ffp-contract=off`. WASM compilation and linking request `-msimd128 -msse2`, no
pthread/pool/shared memory, `DYNAMIC_EXECUTION=0`, ESM and separate WASM. Actual
compile commands and binary memory declarations must be checked after a real build.
The reference community build script is not executed because it directly configures
core as top level and also builds MT/inline variants.

The new C shim uses explicit scalar/uint32 buffers, target-header compile assertions,
and target default constructors. The handwritten facade is statically parsed JS,
not a runtime Function generator. Scratch storage belongs to one facade; copied
snapshots do not alias it, and heap views are reacquired after native calls. Raw ABI
pointers are trusted internal implementation details, not a general untrusted API.
The source does not pretend to offer all old embind APIs or an engine adapter.

## Verified limits and next gates

- Native GCC 14.2 diagnostics can establish behavior of the exact core + C shim,
  not Emscripten, WASM32 layouts, JS facade execution, strict CSP, browser startup,
  asset integrity/loading transactions, contact sampling, or full lifecycle coverage.
- The initial Emscripten preflight BLOCKED receipts remain unchanged. Official
  SDK 6.0.2 is now locally version/provenance verified, and both fresh c Debug and
  Release builds pass real Node physics, ownership and artifact audits under the
  updated lock. Source and layout success is not full toolchain qualification.
- Non-isolated browser and strict-CSP binding fixtures remain unrun in this
  increment, with browser infrastructure blocked. Full T04–T07/G1 cannot pass
  merely because these source files or finite Node test results exist.
- Contacts/events, complex cooking, joints, app prepare/cleanup, browser loader,
  sensor/CCD contracts, MT/replay and complete adapter integration are not delivered
  by this foundation. The historical C16 native fix is not recovered or replicated.

## Additional real diagnostic finding

Both ordinary GCC Debug and Release foundation fixtures pass their numerical
checks. The additional ASan/UBSan run fails at an upstream SSE2 unaligned double
load during the closest-ray test. A header-only minimal fixture reproduces it.
See `patches/README.md` and retained raw diagnostics. An unapplied candidate passes
only its focused UBSan test; full sanitizer acceptance stays FAIL. ASan/LSan has
an additional ptrace limitation on this host. Neither finding changes the pinned
core nor excuses the remaining sanitizer/browser/complete-G1 gates.
