Bottom line
The N4 packet/native path already represents target, teleport and paired clear. The next patch is an ownership/lifecycle/write-authority patch, not another native planner. Merely adding three branches to submitCommand would leave five concrete failures: missing persistent-grant composition/capacity, velocity conflicts without per-body admission, protected cleanup after incompatible type/disable transitions, disabled-teleport Node writeback, and persist-node scene transfer.

2. Minimal ordered internal patch
A. Add a private target record to the existing WorldCommandOwner, keyed by the owned logical body AND its exact initialized RigidBody/adapter identity. Store a unique handle identity, current app/world generation, active/revoked/awaiting-zero/settled state, copied ancestry, and persistent transform lease. Acquire only in ready/unpaused configuration after resolving an actual live enabled native kinematic body. One active/protected owner per body. Publish no handle until all registration/allocation succeeds; on failure release provisional leases without inventing a protected obligation. Handle methods expose only setTarget/clear/dispose. clear queues target-clear and retains ownership; dispose invalidates the handle immediately and creates a protected obligation, is idempotent, and cannot release velocity/transform control early.

B. Add internal motion admission through the same current-world latched queue path as dynamic commands. Target set/clear require the exact live handle plus enabled native type 1; teleport requires initialized actual type 1 or 2 and permits disabled bodies. Keep source/handle validation and every original pose/options getter inside withSubmissionAdmission, with the temporary fence held through its return/throw (owner.ts:366–420). Repeat type/enable/identity checks in prepareCommandTick:486–501. Existing PhysicsBodyCommandInput excludes motion (physics-command-submission.ts:28–40), so add a private AIR motion route rather than falsely treating public dynamic force routing as already sufficient. A retained stale handle invoked from a current producer must reach the CURRENT collecting queue before rejection, analogous to rigid-body.ts:153–158; a closure that rejects only in an old closed owner would not latch the current candidate.

C. Close persistent exact-write authority before any target can become active. node-motion-guard.ts:32–47 creates a real ancestry lease, but no actual owner uses it. NodeTransformGuardLease has only dispose/write (node-transform-validation.ts:12–15); write checks sequence exhaustion only at 106–107. owner scope.write at 1471–1489 grants only the temporary transform lease. Node entry at 138–175 requires a matching grant from EVERY covering lease, so adding one persistent lease currently makes valid writeback reject.
  Add a private pure grant-capacity check/reservation (or continuously protected renewal) to the neutral lease. Before apply, count every planned position+rotation write for each covering persistent lease, including writable physics ancestors; world epoch headroom alone is insufficient. Compose the temporary lease and every same-owner persistent lease around exactly ONE setter call using identical frozen expected values. Never dispose/re-register persistent protection to permit writeback; foreign ownership remains refusal. Preserve world-writeback.ts:235–268 independent expected-local derivation and final whole-batch verification. Owner-owned lease release for a protected zero should wait until successful receipt/writeback/tick settlement, or terminal cleanup, not blindly mirror queue.finishCommit before possible readback failure.

D. Add target-specific velocity admission, not a permanent blanket MutationGuardLease. Current public velocity gate receives only an operation string (physics-command-submission.ts:135–147; Cocos rigid-body.ts:650–676), so it cannot distinguish a protected body. Pass/resolve the actual source and reject target-active OR protected state before reading vector getters. Cover direct adapter setters at AIR rigid-body.ts:189–201 as well. Retain the existing global phase/configuration refusal during producers. A permanent generic mutation guard on the entire component would also block enabled/type/destroy cleanup (component.ts:133–142, 381–399), contradicting the lifecycle contract.

E. Add target-only lifecycle settlement; existing whole-body retirement is insufficient. Wire actual onDisable/onDestroy/setType (AIR rigid-body.ts:95–114), shared-body enableRigidBody/detachRigidBody/setType (474–499), and owner component retirement (795–804, 1374–1412). Revoke the exact handle, remove its pending movement, and retain protection until an actual native zero or teardown proof is established. Do not call releaseBodyAfterTeardown on a still-live shared body merely to erase target state: it removes the logical registration permanently (queue.ts:253–269).
  Critical conflict: enableRigidBody(false) keeps native enabled whenever colliders remain (shared-body.ts:479–481). Component disable is therefore NOT native disable or zero proof. Native pairedClear, including cleanup, requires enabled kinematic type (command_bridge.c:162). After type-away or true native disable, an ordinary deferred pairedClear is rejected. For a still-enabled kinematic survivor, settle paired zero through a narrowly owned safe cleanup path before releasing control; for a real disable/type-away, use verified actual state/zero semantics or an admitted pre-transition cleanup, not a guessed JS flag. If zero precedes a later configuration failure, classify that earlier commit honestly and fault as required; it is not rollback. Add an owner-only queue target-settlement method that preserves the live body registration and cannot clear unrelated ownership. Keep unknown native outcomes retained/faulted until terminal teardown. Do not silently change the current dynamic-command rule that type/disable leaves accepted user records for revalidation (owner.ts:453–466); make target-motion cancellation explicit rather than reusing universal cancelPending indiscriminately.

F. Carry committed teleport participants into writeback selection. captureWriteback currently uses writable = state.enabled && state.type !== 0 (shared-body.ts:327), while world-writeback.ts:258–265 demands every body's final Node equal native origin. A disabled teleport changes native origin, gets skipped by the setter loop, and then fails after commit. Explicitly permit exact owned origin writeback for successfully reset disabled dynamic/kinematic bodies, without enabling or waking them. Freeze/reset-participant identity in the tick, derive pose from actual copied native readback, and retain ordinary disabled/static behavior otherwise. Do not adopt the requested target as reached pose or relax final equality.

3. Scene/app boundary is a real missing seam, not solved by component disposal
- Ordinary nonpersist destruction already reaches adapter disable/destroy, then shared native destruction and owner retirement; app.close calls scene release before physicsPreparation.dispose (app.ts:289–306), and world.destroy closes the owner in finally while distinguishing released/unresolved native bodies (world.ts:944–985; owner.ts:1531–1597). Add target cleanup to those existing finally/cleanup-only paths; never let guards prevent closing a faulted app.
- Persist roots are reparented BEFORE old-scene destruction: director.ts:416–432. releaseScene detaches them with node.parent=null:634–650. Persistent target ancestry leases would reject these calls. Even releasing a guard alone cannot fix it: Box3DSceneTransform keeps immutable parent/local baselines (world-writeback.ts:153–173), and owner BodyRecord keeps original ancestry (owner.ts:705–724). Introduce a narrowly authorized actual persist-transfer transaction that prevalidates/preserves the intended native-origin and affine basis, transfers ancestry/leases continuously, and updates trusted baselines only after verified transfer. The present exact-write grant supports only world position/rotation, not reparent, so there is no existing transfer permission to reuse. Do not sweep all handles on session generation change: the native world survives app.run/releaseScene, and unrelated persist ownership must survive. Until this seam is reviewed, do not claim full target lifetime support.
- System pause is already a prepared queue+producer transition (owner.ts:933–1115): preserve target/protected leases, discard movement, reject paused submissions, resume with no old movement. autoSimulation=false is scheduling only. Game/application/background pause still has no explicit owner reason/manual-clock distinction; app.releaseScene uses game.pause (app.ts:271–273), while StepClock.begin deliberately also pauses the game (step-clock.ts:103). Do not infer semantic command pause from game.isPaused, or consume/zero by adding a second loop.
