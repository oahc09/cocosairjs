Read this before implementing an AIR visual creation or recreation task, or when pixels look wrong without an exception. For math-only, prose-only or unrelated tasks, skip it. Use the relevant row below to choose one owner and its direct dependencies; do not load the whole suite. These are diagnostic hypotheses, not diagnoses inferred from a screenshot alone.

## Minimal visual feedback loop

1. Establish the requested reference or visual goal and a few observable criteria: subject framing, light/dark hierarchy, readable detail, and the intended motion or interaction. Start with a representative scene slice; do not multiply expensive effects before it is visible.
2. Run the current candidate and capture its actual browser/compositor output at the intended viewport after assets are ready. Use available authorized browser tooling; a console without errors, successful build or GPU readback alone is not a view of the final picture. This skill ships no capture service or browser installation.
3. Inspect the image against the reference or stated goal. Name a concrete mismatch and a falsifiable cause, such as clipped skyline, crushed shadows or subpixel windows. Change the smallest relevant parameter group, capture again under the same conditions, and compare. Do not change camera, fog, exposure and geometry together when diagnosing one failure.
4. For motion, inspect separated representative times or the relevant interaction state; a single still cannot establish animation. During ordinary viewing retain native pacing. For controlled assertions pause and use the project's single step clock, then restore native pacing.
5. Stop when the requested criteria are met and the affected behavior is checked. If further iterations stop improving the result or tooling/budget blocks inspection, report the concrete remaining mismatch and verification limit. Preserve the final capture and identify its candidate and viewport; do not label an unviewed result visually verified.

Fog density, orbit distance, rain length and window spacing depend on scene scale and projected size. Tune them from observations, not copied magic numbers. Separate API correctness, application logic, composition and measured rendering limits when reporting causes. A successful skill lookup establishes none of these by itself.

When a new trap is reproduced, distinguish an API contract from a scene-specific bug or artistic choice. Return confirmed reusable guidance to its existing owner with source/version evidence and a symptom term; keep unverified explanations as hypotheses. Only update persistent agent memory when the user explicitly requests it. No claim about skill coverage or visual success rate follows from this workflow without a separate evaluation.

## A flat full-screen color can be a framing failure

If a known valid shader fills the screen and the subject's silhouette disappears, compare an earlier wide view before treating it as a material defect. For an orthographic camera, moving farther away does not change projected size. Automatic fitting needs mesh/model bounds; hand-authored static `createMesh` geometry does not calculate them by default. Follow the [bounds prerequisite and repair](../../cocosair-camera/references/camera-projection.md#frameobject-moves-the-camera-but-an-orthographic-subject-stays-cropped), then capture the same viewport and confirm the subject and margins have returned. Keep the failed screenshot as evidence of why the first repair was insufficient.
